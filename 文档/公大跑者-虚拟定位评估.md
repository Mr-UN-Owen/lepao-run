# 公大跑者 · 虚拟定位可行性评估

> **案例说明**：本文是 2026-11 对某公安院校「公大跑者」小程序的**案例评估**，只记录判断路径与技术结论，不构成对任何学校或平台的指控、建议或背书。
> 文中出现的学校名、`school_id`、跑区名仅用于定位案例对象。

> 结论先行：**定位本身能改，"改定位"不等于能过审。** 公大跑者的判定不在手机端，而在服务端对
> 「轨迹 + 打卡点首通过 + 配速 + 步频 + 每日唯一」的组合校验。单纯把坐标搬到操场，最可能的结果是
> 记录被异步作废，而不是拿到里程。

本文只做技术评估与实现路径，不含任何账号/代跑服务。

「随机 2 个打卡点 + 跑区 + 每日 1 次 + 配速区间」这套组合，与工作区已复现的
`beforeRunV260 → log_data(首通过) → stopRunV278` 语义一一对应（见 `docs/研究记录.md` §5、§7.3）。
所以**第一件该做的事不是装虚拟定位，而是确认它的后端域名**。

## 2. 先判定后端（5 分钟，零风险）

用本仓库的零依赖嗅探代理，不解密、不装证书、只看域名与 SNI：

```bash
python 工具/proxy_sniff.py            # 监听 127.0.0.1:18081
```

1. Windows 设置 → 网络和 Internet → 代理 → 手动 `127.0.0.1:18081`
2. 电脑微信 → 打开「公大跑者」→ 进入跑步页 → 点一次"开始跑步"
3. 看控制台 / `_private/sniff.log`

判定表：

| 看到的域名 | 判定 | 下一步 |
|---|---|---|
| `*.lptiyu.com`、`/v3/api.php/` | 乐跑系，与本仓库同后端 | 直接走 §3 协议路线，**不需要虚拟定位** |
| `xxx.edu.cn` + `v3/index.php` | 学校白标部署的同一套 v3 | 同上，改 `lepao/v3api.py` 的 BASE |
| `servicewechat.com/<appid>` | 小程序框架，只是外壳 | 继续看业务域名 |
| 其他（体适能 / 闪动 / 自建自研） | 换平台 | 走 §4 的端侧方案，反作弊面需重新摸 |

## 3. 若确认是乐跑系：绕开定位，直接跑协议

虚拟定位解决的是"手机骗过自己的定位"，协议路线解决的是"服务端收到一条真人形态的轨迹"。
后者不依赖任何 Hook，且本仓库已把整条链复现完（`lepao/pipeline.py`）。

```bash
# 1) 登记成员（本人 / 已明确同意的同学）
py -3 cli.py account add <学号> <卡号> --alias <姓名>
# 2) 抓号：起 mitm → 你开小程序到跑步首页 → token 归位
py -3 cli.py capture --member <姓名>
# 3) 干跑（零写入，验证跑区/打卡点/额度/轨迹覆盖）
py -3 cli.py build --member <姓名>
# 4) 提交 + 复核
py -3 cli.py submit --member <姓名>
py -3 cli.py watch <record_id> --member <姓名>
```

关键差异点（换学校/换站点时必须核对）：

- `beforeRunV260` 返回的 `run_zone_list` / 打卡点坐标 → 决定轨迹必须覆盖哪两个点；
- `log_data` 的 `distance` 必须是**首通过时累计公里**，不是 haversine 米（`docs/研究记录.md` §7.3 的坑）；
- `step_info` 桶数与数值区间要和 `used_time` 自洽；
- 每日额度 1 次，禁止并发提交。

若公大站点域名不是 `api2.lptiyu.com`，改 `lepao/v3api.py` 里 `BASE` 与 `lepao/transport.py` 的
`Host`/`referer`（referer 要换成公大跑者的 `servicewechat.com/<appid>/<ver>/page-frame.html`），
算法层（AES-128-CBC + SignMD5 + random6）无需改动。

## 4. 端侧虚拟定位：能不能骗过校验

### 4.1 为什么"直接开模拟定位"没用

微信小程序的 `wx.getLocation` 走的是**微信客户端自己的定位通道**（腾讯定位 SDK + XWeb 容器），
不是系统 `LocationManager` 的 mock provider。所以在开发者选项里挂一个"模拟位置信息应用"，
大部分机型上小程序照样返回真实坐标——这就是很多人反馈"改了没反应"的原因。

Android 侧还有第二道：`Location.isFromMockProvider()`。即使坐标进来了，标记为 mock 也会被丢。

### 4.2 Android：可行路线是 Hook，两段都要做

| 段 | 要解决 | 现成模块 |
|---|---|---|
| 定位段 | 把小程序定位接口重定向到系统定位接口，让模拟位置真正生效 | `cc.hakurei.wxhooklocation`（HookWXMAppLocation，LSPosed，勾选微信） |
| 坐标段 | 提供轨迹级移动（步行/跑步速度、GPS 抖动） | FakeLocation 系（`dev.lerist.fakelocation` 的 root/Xposed 形态）、`com.yinshibai.location` |
| 传感器段 | 加速度计 / 计步器 / 步频 | DragonRun 类模块（改写三类传感器事件，步频锁 172–182 步/分） |

要点：

- FakeLocation 官方条款明确把"校园跑"类应用放进屏蔽名单，正常安装会被识别 → 需要 Xposed 形态或改包名；
- **只做定位、不做传感器**，在有步频校验的站点上会被判"打点异常/无效"；
- Root 本身会被部分校园跑检测（设备指纹），可行组合是 LSPosed（Zygisk）+ 隐藏 Root + 只勾微信。

### 4.3 iOS：能改坐标，改不了运动学

爱思助手 / AnyGo / iAnyGo 这类工具改的是**设备级 CLLocation**，小程序读到的坐标会变；
但加速度计是真实硬件数据，无法通过改定位伪造。社区实证（贴吧、校园跑技术贴）表现为
"路线能画出来，但不记公里数 / 判定无效"——正是缺了步频与速度曲线的自洽。

### 4.4 无 Root 虚拟机路线为什么不适合小程序

Ac-Wiki 的 VMOS Pro + 影梭方案针对的是**独立 APP**（阳光长跑、闪动、步道乐跑）。
公大跑者是微信小程序，必须把整个微信搬进虚拟机才能生效：登录风控、摄像头、性能都是坑，
投入产出比远低于 §3 的协议路线。

## 5. 服务端校验维度对照

| 校验项 | 手机端能否伪造 | 协议路线是否天然满足 |
|---|---|---|
| 坐标轨迹 | 能（Hook） | 是（模板相似变换） |
| 打卡点首通过 | 能（要踩点） | 是（pipeline 自动覆盖） |
| 配速区间 | 能（要控速） | 是（pace_factor） |
| 步频 `step_info` | 能（要 Hook 传感器） | 是（分桶生成） |
| 每日唯一 / 额度 | 不能（服务端） | 是（额度预检） |
| 设备指纹 / 极验 | 难 | 是（不复用设备侧） |
| 异步复核作废 | 不能 | 取决于轨迹形态（必须用 template 引擎） |

---

## 6. 落地顺序建议

1. 跑 `工具/proxy_sniff.py` 确认后端域名（5 分钟，决定后面所有事）；
2. 是乐跑系 → 走 §3，完全不需要虚拟定位；
3. 不是乐跑系 → 回到端侧：Android + LSPosed 三件套（定位 Hook + 坐标 + 传感器），iOS 路线只当参考；
4. 任何路线都先干跑验证一次（协议路线用 `cli.py build`，端侧路线先用一次短距离试跑看服务端回执字段）。
